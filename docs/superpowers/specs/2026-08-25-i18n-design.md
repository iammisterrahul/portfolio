# i18n + Cookie Consent — Design

**Date:** 2026-08-25
**Status:** Approved, pending implementation plan

## Goal

Ship the portfolio in five locales with a language switcher in the navbar, plus a
cookie-consent card. Zero new runtime dependencies.

**Locales:** `en` (default), `hi` (Hindi), `ml` (Malayalam), `ar` (Arabic, RTL),
`zh` (Simplified Chinese).

## Scope decisions

These were settled during brainstorming and are not open for reinterpretation
during implementation.

### Translate: UI chrome only

Roughly 60 short strings — navigation, section eyebrows and headings, CTAs,
badges, footer, the consent card.

### Do not translate

Résumé prose and proper nouns stay in English:

- `profile.name`, `profile.summary`
- Job titles, company names, date ranges
- Education entries
- Project names and descriptions
- Technology terms (React.js, Next.js, Web3.js, Tailwind CSS, …)

**Rationale:** machine-quality translation of professional prose is a liability
on the document that represents the author professionally. Stilted copy is worse
than English copy. Date ranges stay English because they sit in the same visual
block as untranslated company names — translating only "Present" would look
worse than leaving the range alone.

### Deliberately out of scope

- `app/opengraph-image.tsx` — stays English. Per-locale OG images would require
  loading script fonts into the image runtime; high complexity, low value.
- `app/manifest.ts` — stays English. Per-locale PWA manifests are overkill here.
- Cookie-based locale persistence — plain links already work and a cookie would
  fight static caching.
- Translating the skills marquee items (technology names).

## 1. Routing

`app/[locale]/` becomes the only page tree, with the **root layout inside it**.
This is required: `<html lang dir>` must vary per locale, a nested layout cannot
change `<html>`, and setting it from an inline script (as the theme currently
does) would serve crawlers the wrong `lang`.

```
app/
  [locale]/
    layout.tsx          # was app/layout.tsx — sets lang, dir, locale font
    page.tsx            # was app/page.tsx
  i18n/
    config.ts
    get-dictionary.ts
    dictionaries/
      en.ts             # source of truth, exports Dictionary type
      hi.ts  ml.ts  ar.ts  zh.ts
```

`app/layout.tsx` and `app/page.tsx` are deleted (moved). `app/sitemap.ts`,
`app/robots.ts`, `app/manifest.ts`, `app/opengraph-image.tsx`, `app/globals.css`
and `app/data/resume.ts` stay at the `app/` root.

`generateStaticParams` returns all five locales, so all five routes prerender.
No middleware, no runtime locale negotiation.

Everything currently in the root layout's `<head>` moves with it into
`app/[locale]/layout.tsx`: the pre-paint theme script (unchanged) and the JSON-LD
block. The JSON-LD `inLanguage` field must become the active locale rather than
the hardcoded `"en"`, and `<Analytics />` / `<SpeedInsights />` stay mounted as
they are.

### URL shape — English stays at `/`

The site is already indexed at `/`. Keeping that canonical URL requires two
entries in `next.config.ts`:

```ts
rewrites:  [{ source: "/",   destination: "/en" }]   // serve English at root
redirects: [{ source: "/en", destination: "/",  permanent: true }]
```

Next.js evaluates redirects before `beforeFiles` rewrites, and an internal
rewrite target is not re-run through redirects, so these do not loop: `/en`
redirects out to `/`, and `/` internally serves the prerendered `/en` tree.

Resulting URLs: `/` (en), `/hi`, `/ml`, `/ar`, `/zh`.

**Implementation must verify the no-loop behaviour in the browser**, not assume
it from the routing-order docs.

## 2. Dictionaries

`en.ts` is the source of truth and exports its own type. Every other locale is
annotated with that type, which makes TypeScript the key-parity check:

```ts
// dictionaries/en.ts
export const en = {
  nav: { about: "About", skills: "Skills", /* … */ },
  hero: { badge: "Available for new opportunities", /* … */ },
  // …
};                              // NOTE: no `as const` — see below
export type Dictionary = typeof en;

// dictionaries/ml.ts
import type { Dictionary } from "./en";
export const ml: Dictionary = { /* … */ };  // missing key => tsc error
```

**`en` must not be declared `as const`.** With `as const`, every value becomes a
string *literal* type, so `Dictionary` would require `ml.nav.about` to be exactly
`"About"` — the annotation would reject every actual translation. Without it,
`typeof en` widens values to `string`, which enforces key parity while leaving
values free. This is the one detail that makes or breaks the whole approach.

`.ts` rather than `.json` specifically to get this. A key forgotten in Malayalam
fails the build instead of rendering a blank spot in the UI. This removes the
need for a key-parity test.

`get-dictionary.ts` maps locale → dynamic `import()`, server-side only. **No
translation data reaches the client bundle.**

`config.ts` exports:

```ts
export const locales = ["en", "hi", "ml", "ar", "zh"] as const;
export type Locale = (typeof locales)[number];
export const defaultLocale: Locale = "en";
export const localeNames: Record<Locale, string>;  // English, हिन्दी, മലയാളം, العربية, 中文
export function dir(locale: Locale): "ltr" | "rtl";  // rtl only for "ar"
```

### Strings moving out of `app/data/resume.ts`

- `navLinks` — labels move to the dictionary, keyed by anchor id. The `href`
  values stay in `resume.ts`.
- `stats` — `label` moves to the dictionary; `value` stays (numerals).
- `skills[].category` — moves to the dictionary. `skills[].items` stay.

`profile`, `experience`, `education`, `projects` and `marqueeSkills` are
untouched.

### Strings moving out of components

`Hero` (badge, "Hi, I'm", both CTAs), `About`, `Skills`, `Experience`,
`Education`, `Projects` (eyebrow/title/description, "Freelance" badge, the
`sr-only` "(opens in a new tab)"), `Contact` (eyebrow, heading, paragraph, "Say
hello", channel labels, `sr-only` suffix), `Footer` (the built-with line),
`Navbar` ("Let's talk", "Toggle menu"), `ThemeToggle` ("Toggle color theme").

Components are Server Components and receive their strings as props from
`page.tsx`. The three existing client components (`Navbar`, `ThemeToggle`,
`ScrollProgress`) and the two new ones receive strings as props too — they must
not import dictionaries directly.

## 3. Language switcher

New: `app/components/ui/LanguageSwitcher.tsx` (client component), placed in the
navbar beside `ThemeToggle`.

- Globe icon trigger + dropdown listing all five locales.
- **Each language is labelled in its own script** — English, हिन्दी, മലയാളം,
  العربية, 中文.
- The site is one page with hash anchors, so switching preserves the current
  hash: `/ar#projects`.
- Accessibility (the codebase just had an audit; do not regress it):
  `aria-expanded` on the trigger, `role="menu"` / `role="menuitem"`, Escape to
  close, arrow-key navigation, focus returned to the trigger on close,
  `aria-current` on the active locale. Visible text must be part of the
  accessible name — the same WCAG 2.5.3 rule the recent fixes addressed.

## 4. Cookie consent card

New: `app/components/ui/CookieConsent.tsx` (client component), mounted in
`app/[locale]/layout.tsx`.

**Known limitation, accepted by the user:** the site currently sets no tracking
cookies. Vercel Analytics and Speed Insights are cookieless, and the `theme`
`localStorage` key is a functional preference. So this card gates nothing today.
It exists as correct scaffolding for adding Google Analytics later.

Design:

- A dismissible **card**, not a blocking modal — bottom corner, using existing
  tokens (`glass`, `border-border-soft`, `bg-card`, the `accent-1 → accent-3`
  gradient for the primary action). Must not trap focus or block page content.
- Accept / Decline buttons. Choice persists in `localStorage` under
  `cookie-consent` (`"granted" | "denied"`); the card renders only when unset.
- Follows the `ThemeToggle` pattern: a `mounted` guard so the server render and
  first client render agree, and `try/catch` around all storage access.
- Exports `hasAnalyticsConsent(): boolean` plus a comment marking the single
  place to mount an analytics script once consent exists.
- Strings live in the dictionaries like everything else, and it gets the same
  RTL treatment.

## 5. RTL

`dir` is set from the locale on `<html>`. The direction-sensitive utilities were
inventoried — approximately 15 real fixes, not a rewrite.

**Convert to logical properties:**

- `pl-8`, `pl-12`, `left-[9px]`, `left-[7px]` — Experience and Education
  timeline rails → `ps-*`, `start-*`
- `mr-1` (active nav dot) → `me-1`
- `right-0` → `end-0`
- `ArrowIcon` hover `translate-x-1` → mirrored with an `rtl:` variant

**Leave alone:**

- `left-1/2 -translate-x-1/2` — direction-neutral for centred elements
- Decorative blob positions (`left-24`, `left-1/3`) and `bg-gradient-to-*`
  fills — purely aesthetic
- The skills marquee — decorative logo strip; reversing per-locale buys nothing
- The `-rotate-45` external-link arrows

**Verify visually, do not assume:** the scroll-progress bar should fill from the
right under `dir="rtl"` because it is an in-flow block, but this must be
confirmed in the browser.

## 6. Fonts

Loaded per-locale in `app/[locale]/layout.tsx` so English keeps shipping only
Geist:

| Locale | Font |
|---|---|
| `en` | Geist / Geist Mono (unchanged) |
| `hi` | Noto Sans Devanagari |
| `ml` | Noto Sans Malayalam |
| `ar` | Noto Sans Arabic |
| `zh` | Noto Sans SC |

`next/font/google` requires top-level constant calls, so all five are declared at
module scope and only the matching locale's className is applied. Unused faces
are built but never requested by the browser.

**Accepted cost:** Latin subsets well, CJK does not. `/zh` will be meaningfully
heavier than the other locales. This is inherent to shipping Chinese.

Geist has no Arabic, Devanagari, Malayalam or CJK glyphs, so this step is what
prevents four of the five locales rendering as tofu. It is not optional polish.

## 7. SEO

- `generateMetadata({ params })` per locale — title and description from the
  dictionary.
- `alternates.canonical` per locale, plus `alternates.languages` covering all
  five on every page.
- `openGraph.locale` mapped: `en_US`, `hi_IN`, `ml_IN`, `ar`, `zh_CN`.
- `app/sitemap.ts` — five entries with language alternates.

## 8. Verification

The repo has no test infrastructure (no test script, no test dependencies), and
the `Dictionary` type already enforces the property a parity test would check.
No test harness is proposed. If the user wants one, that is a separate decision.

Gates:

1. `npm run lint`
2. `npx tsc --noEmit`
3. `npm run build` — confirm **five** prerendered routes
4. Browser checks:
   - `<html lang>` and `<html dir>` correct on each of the five locales
   - `/` serves English and `/en` redirects to `/`, with no redirect loop
   - Switcher navigates between locales and preserves the hash
   - RTL visual pass on `/ar` — timeline rails, nav dot, arrows, progress bar
   - No tofu glyphs on `/hi`, `/ml`, `/ar`, `/zh`
   - `hreflang` alternates present in the served HTML
   - Consent card: appears once, choice survives reload, does not trap focus

## Risks

| Risk | Mitigation |
|---|---|
| Rewrite/redirect loop on `/` | Explicit browser verification; fallback is prefixing every locale and redirecting `/` → `/en` |
| Untranslated prose beside translated chrome reads oddly | Accepted trade-off; chrome-only was the deliberate choice |
| `/zh` page weight from CJK font | Accepted; per-locale loading keeps other locales unaffected |
| Consent card gates nothing today | Documented above; scaffolding for future GA |
| RTL regressions in untested spots | Full visual pass on `/ar` is a release gate |
